# EPIC plant-based diet proteomics and Mendelian randomisation

R analysis scripts by Peggy Ler supporting analyses of hPDI and uPDI protein
signatures in EPIC, disease associations, Mendelian randomisation,
colocalisation, enrichment and protein contextualisation.

This follow-up package contains **67 R scripts in six folders**. Add these
folders beside the existing `signatures/` folder, and use this README at the
repository root. The previously prepared 21 signature scripts are not duplicated
in this ZIP. No study data, fitted models or generated results are included.

The code has been organised and statically checked. It is **not yet a validated
end-to-end reproduction of the article**. Resolve the review items below and
compare fresh outputs with the article before describing it as such.

## Set local paths

Start a fresh R session for each script and set the working directory to the
repository root. Open the script and edit its path settings directly:

```r
PROJECT_ROOT <- "."
DATA_DIR <- file.path(PROJECT_ROOT, "data")
OUTPUT_ROOT <- file.path(PROJECT_ROOT, "outputs")
```

`DATA_DIR` can instead point to your authorised local data directory. Use the
same `OUTPUT_ROOT` as the signature scripts. Follow-up figures and tables go
under `outputs/manuscript`; signature artefacts remain under `outputs/hpdi`
and `outputs/updi`. Source-script paths are derived from `PROJECT_ROOT`.
When one script sources another, keep their path settings consistent.

Where present, also edit `HPDI_RUN`, `UPDI_RUN` and `LIMMA_DATE`. Defaults retain
the original April 2026 runs and LIMMA date; they do not silently select newer
results. GBM scoring scripts 1_2 and 1_3 use `current_run_dir.txt`: its contents
must point to the same intended run selected in 1_1 and downstream scripts.
Update that pointer when moving saved outputs to another computer. Filenames
and outcome manifests inside scripts remain directly editable.

For example, from the repository root:

```r
source("mendelian_randomisation/3_1_proteins-genenames_cleaning.R")
```

Do not upload participant data, prediction exports, local credentials or
generated model bundles with these scripts. Outputs are local analysis files;
many scripts deliberately overwrite named tables when rerun.

## Follow-up running order

The numbering reflects the original scripts, not a single linear pipeline.
Run the relevant branches once their inputs exist.

1. **Signature discovery:** use the separate `signatures/` scripts described
   later in this README. Retain the exact model run, preprocessing and data
   versions used for the article.
2. **Score the analysis cohort:** in `scoring_and_signatures/`, run 1_1 before
   GBM scoring 1_2/1_3, and run elastic-net scoring 1_4/1_5 and LIMMA scoring
   1_6. Review the preprocessing concerns below before using new scores.
   Script 1_7_1 is a diagnostic based on the supplied historical scored-cohort
   input; it does not automatically read freshly exported 1_6 scores.
3. **Prepare protein lists:** run MR scripts 3_1 and 3_3 to map signatures to
   gene metadata. Then run 1_7_0 for LIMMA supplementary lists and 1_8 to add
   bootstrap/GBM information. Top-protein plots 1_7_2/1_7_3 also need reviewed
   cis-instrument tables. Volcano plots 1_7_4/1_7_5, overlap 1_9 and SHAP
   ranking 8 use the corresponding preceding tables.
4. **Survival analyses:** run 2_0 to join the current scores and prepare
   `df_sel`, then 2_1/2_2/2_3 for cancer/T2D/CVD. Run 2_4 to combine their
   coefficient workbooks and 2_5 for the GBM sensitivity analysis.
5. **MR:** after mapping, run 3_2 for hPDI cis instruments and 3_4 for uPDI.
   Complete/document manual curation as needed, then run 3_6/3_7, followed by
   3_8 and 3_9. Script 3_5 is an optional helper with example loci, not an
   automatic stage that completes the manual curation.
6. **Colocalisation:** configure and run the required 4_1–4_8 analyses after
   confirming their outcomes, exposure tables and local summary statistics.
   Then run 4_9 to combine results. This collection does not establish that
   every article outcome has a complete, matching run script.
7. **Enrichment:** 5_1/5_2 use the compiled signature lists; 5_3/5_4 require
   `MR_all_source_sigresults_with_coloc.csv` from 4_9 and the selected cis
   instrument tables.
8. **Contextualisation:** run 6_0_0 for age functional forms, then 6_0 and 6_1
   for hPDI/uPDI functional forms. Script 6_0_1 is an additional diet-shape
   analysis. Run the sex, smoking, PA, alcohol and age interaction models
   (6_2–6_7, including 6_6_1/6_6_2, and 6_9_age), then the associated 6_8
   plotting scripts and 6_9_1 table. Some plotting scripts contain manually
   specified protein/functional-form selections. **7_0 needs the missing
   intended alcohol plotting script before it can run completely.**

## Background universe for signature enrichment

Scripts 5_1 and 5_2 use a shared background of all assayed protein IDs, as
confirmed by the author. The full hPDI LIMMA export supplies that inventory:
the code takes its entire `protein` column, without filtering on significance
or using hPDI effect estimates or p-values to construct the background.
Its hPDI filename identifies where the inventory is stored, not a selection
of hPDI-associated proteins.

The background IDs are mapped to unique, non-missing ENTREZ gene IDs, which
are passed as `universe = bg_entrez`. The separate hPDI or uPDI signature lists
provide the genes tested for enrichment. Existing comments record 7,285 assay
IDs and 6,367 mapped background gene IDs; these historical counts were not
recalculated during cleanup. No background-selection calculations were changed.
This description applies to signature-enrichment scripts 5_1/5_2.

## Signature discovery workflow

R analysis scripts by Peggy Ler for hPDI and uPDI protein discovery in the EPIC
subcohort. The signatures folder contains LIMMA, elastic-net and XGBoost
signature analyses. No participant data or fitted outputs are included.

### Files

- `signatures/`: full-subcohort LIMMA and elastic-net scripts.
- `signatures/gbm/hpdi/`: hPDI XGBoost scripts.
- `signatures/gbm/updi/`: uPDI XGBoost scripts.

The GBM folders use the `xgboost` R package. Keep each `00_data_prep*.R` file in
its corresponding GBM folder: scripts 01–05 source that helper automatically.
The package needs no separate configuration folder or launcher.

### Before running

1. Set the R working directory to the repository root containing this README
   and the `signatures` folder. Start each script in a fresh R session.
2. Edit `DATA_FILE` and `OUTPUT_ROOT` near the top of each script you run.
   Use the same input file and output root throughout a workflow. Forward
   slashes work in Windows paths. Defaults are `data/subcohort_20251106.RData`
   and `outputs`; no such data file is provided.
3. The RData file must contain a data frame named `subcohort`, including the
   appropriate numeric diet score (`Hpdi_NoVegoils` or `Updi_NoVegoils`), numeric
   protein columns beginning with `seq`, and the required covariates below.
4. Install the required packages, preferably matching the original analysis
   environment: `limma`, `statmod`, `glmnet`, `dplyr`, `tibble`, `readr`,
   `data.table`, `Matrix`, `xgboost`, `caret` and R's bundled `splines`.
   Original R/package versions were not supplied with these scripts.

Covariates are `Sex`, `Age_Recr`, `L_School`, `alc_freq`, `smoke`, `Center` and
physical activity. LIMMA/elastic net use `PA_total_MET_quint`; GBM uses
`PA_total_MET`. Smoking and alcohol variables must include the reference value
`Never`. Education is recoded from `L_School` (0/1; 2/3/4; 5/missing).
`Idepic` is an optional ID column used in elastic-net prediction exports.

For example, open a script in RStudio and use Source, or run from the repository root:

```r
source("signatures/Limma.R")
```

Output folders are created automatically. Keep your local data, generated
outputs and private file paths out of the public repository. Outputs include
participant-level predictions, prep bundles and SHAP matrices.

### Running order

#### Full-subcohort LIMMA

Run `signatures/Limma.R` for hPDI and `signatures/Limma_uPDI.R` for uPDI.
These are independent association analyses and use linear age adjustment.

#### Elastic net

Run 1.1 → 1.2 → 1.3 separately for each outcome:

| Step | hPDI file in `signatures/` | uPDI file in `signatures/` |
|---|---|---|
| Split; training-only LIMMA filter | `1.1_Preprocess_ENET_hPDI_with_filter.R` | `1.1_Preprocess_ENET_uPDI_with_filter.R` |
| Tune; fit; bootstrap | `1.2_Train_Lasso_hPDI.R` | `1.2_Train_Lasso_uPDI.R` |
| Test-set evaluation | `1.3_Test_Lasso_hPDI.R` | `1.3_Test_Lasso_uPDI.R` |

Historical filenames contain `Lasso`, but the main models search elastic-net
alpha values 0.1, 0.3, 0.5, 0.7 and 0.9. Outputs are saved under `hpdi/` and
`updi/` within your chosen output root. Training uses 1,000 bootstrap replicates.
The training/test scripts require exactly one matching prep/model RDS in the
outcome folder. Use a separate output root for a separate analysis run to avoid
overwriting files or mixing model versions.

`1.2_Train_Lasso_uPDI_alpha1.R` is an optional wider alpha grid (0.1–1.0 in
steps of 0.1). It is not part of the default sequence and does not fix alpha at
1. It reads the main uPDI prep file and writes separately under
`updi/alpha_grid_01_to_10/`. The supplied 1.3 script evaluates the main model.

#### XGBoost / GBM

Within each outcome's GBM folder, run the numbered scripts in order:

| Prefix | Step |
|---|---|
| `01_` | Tune tree structure; create and save the split/CV folds |
| `02_` | Tune regularisation |
| `03_` | Tune column sampling |
| `04_` | Fit the final model and evaluate the test set |
| `05_` | Compute SHAP values and summaries |

The `00_` files are sourced helpers and should not be run independently.
Stage A creates a timestamped run directory under `<outcome>/gbm/` and saves
its location in `current_run_dir.txt`. Subsequent stages use that same run.
Re-running Stage A selects a new run for subsequent stages. Keep the same data,
row order and output root; if you move saved outputs, update the pointer file.
The grids refine earlier broad searches that are not included in this upload.
The supplied setting of 16 XGBoost threads is retained.

### Reproducibility notes

- The duplicate post-filter scaling of diet score and age was removed from
  both 1.3 test scripts. Earlier scaling remains, matching 1.1. Peggy reported
  unchanged results after rerunning 1.3; numerical outputs were not provided
  for independent verification. Existing fitted models can be used for this check.
- The elastic-net split uses seed 258 and the bootstrap uses seed 42. The
  fitting scripts do not fix a CV seed or use a shared `foldid` across alphas;
  rerunning training can therefore choose different tuning parameters.
- Elastic-net test R2 is squared Pearson correlation; GBM test R2 is
  `1 - SSE/SST`. They are different definitions and need explicit labels when
  compared. Both calculations remain as supplied.
- Predictive preprocessing scales age and the outcome before splitting.
  Protein preprocessing is assumed to have occurred upstream; ENET uses
  `standardize = FALSE`, while GBM replaces missing protein values with zero.
  Confirm these choices and the differing physical-activity covariates against
  the manuscript. ENET's protein filter is fitted on the full training split,
  outside the subsequent internal CV folds.
- The SHAP signed-weight calculation uses the sign of the mean SHAP
  contribution. This alone does not establish the direction of the
  protein-abundance relationship. Its numerical calculation is retained.
- In GBM tuning, the column `proteins_used` counts all used features, including
  covariates. Stage 04 separately extracts protein-only features. Historical
  commented results are annotations, not outputs verified during cleanup.
- The five alternative hPDI scripts originally nested inside `files.zip` are
  omitted from this simpler upload. The surrounding hPDI scripts are retained;
  confirm that these are the manuscript-producing versions before final release.

The scripts have been checked with an R syntax grammar parser. A native R
runtime and study data were unavailable during cleanup, so the full workflow
has not been executed or numerically validated here. Record `sessionInfo()`
when running in the original analysis environment.
